## 1. 一句话定位

**知行小课：读懂一条知乎建议，试出自己的答案。**

产品把一篇知乎赛事知识内容转成连续的学习工作台：用户可以直接让 AI 拆解主张、论证步骤和适用边界，也可以先写自己的复述再核对；随后完成一个一分钟理解挑战、继续追问，并把建议改成一个有完成标志的“待尝试”小行动，最后导出 Word 学习卡。

我们不把“生成了答案”说成“用户已经学会”，也不把“导出卡片”说成“行动已经完成”。

## 2. 目标用户与真实使用场景（待试用验证）

首版目标用户假设是想改善学习方法、但经常“看过建议却不知道怎么用”的大学生或初入职场学习者。以下是待真实试用验证的场景，不是已统计的用户数据：

- 备考或做作业前，面对一条笼统的学习建议，不知道今天具体从哪里开始。
- 看完一篇方法文章后，想确认自己是否漏掉了条件，而不是只凭“我同意”判断理解。
- 已经尝试过一次学习计划，想把事实、解释和下一步分开记录，再只改变一个变量。
- 有明确的课程、题型、时间或卡点，希望把通用建议改成自己的小行动。

首版暂不承诺长期打卡、账号体系、教材上传、复杂知识图谱、语音或全站搜索。

## 3. 核心流程与产品价值

1. **选内容**：从知乎知识接口实际返回的列表中选择条目，在已加载的标题、摘要内筛选。
2. **读懂或复述**：
   - “AI 帮我读懂”无需预先填写文字；
   - “我先说说理解”保留用户原话，再让 AI 带引用核对。
3. **核对依据**：核心观点、作者公开论证步骤和适用条件标为“原文理解”，逐条引用当前文章片段；批判性提醒、构造场景、追问和行动标为“AI 延伸”。
4. **一分钟挑战**：回答一个能由当前片段核对的问题；反馈只说明关键点是否覆盖，有遗漏时追加一个变式题，不评分、不宣称掌握。
5. **继续追问**：每条回答绑定当前文章中可逐字定位的引用；资料不足时明确说明当前片段无法判断。
6. **场景化行动**：输入课程/任务、可用时间、目标产出或卡点，重新生成任务、完成标志和回顾安排；三者必须因场景而改变，状态仍为“待尝试”。
7. **带走学习卡**：浏览器本地生成 Word（`.docx`），包含来源、生成方式、引用、复述/追问、挑战、场景和行动编辑记录。

价值在于把“读过一条建议”推进到“能核对、能提问、能做一次小实验”，同时保留证据和内容归属。

## 4. 知乎内容/API 边界

首版只使用比赛专用的两个无鉴权 GET 接口：

```text
GET https://api.zhihu.com/km-indep-home/hackathon/v2/knowledge/list
GET https://api.zhihu.com/km-indep-home/hackathon/v2/knowledge/{work_id}
```

- `work_id` 只接受列表实际返回的十进制字符串，再请求对应详情；服务端不让用户任意拼接未知 ID。
- 当前实现展示标题、作者、来源标识、可读片段及 `completeness: unknown`。2026-09-13 live probe 返回 10 项，抽查作品 `1523701957479239680` 的正文约 3000 字符并有末尾截断信号；这是一次观测，不是接口规模或全文保证。
- 列表标签只作原始展示，不能据此宣称可靠学科分类；“筛选”仅限已加载列表，不能宣传为全知乎搜索、专业课题库或全文检索。
- 空列表、正文为空、网络失败和字段异常展示真实状态；赛前 `npm.cmd run demo` 使用仓库内项目原创材料，并在页面、来源脚注和导出卡中标记“开发演示/非知乎正式内容”。
- 首版不接知乎 OAuth、个人知识库、站内搜索、知乎直答或 CLI；这些能力需要不同凭证/协议，且不是当前核心证据链。

## 5. AI 流程与可信约束

应用后端使用 Responses 形状的模型客户端，默认配置为赛事 provider 地址、`gpt-6-astra`、推理档位 `max`；凭证只从后端环境读取。模型每次只接收当前已获取的文章片段和用户主动提交的复述、问题或场景。

生成结果使用严格 JSON schema 校验：

- 原文相关陈述必须绑定当前段落的逐字引用，并在本地匹配；匹配只证明引文存在，不证明结论绝对正确。
- 讲解与复述核对分开；用户原话不会被 AI 覆盖。
- 追问回答按陈述逐条绑定引用；挑战不评分；行动建议不写成作者原话。
- 页面和学习卡始终区分“原文理解”“AI 延伸”“用户文字”，并标记“待尝试”。
- 生成接口默认校验同源 `Origin`，可配置固定来源、Bearer、HttpOnly 会话 Cookie 或受信任网关凭证；进程级来源窗口限频和累计请求上限用于降低滥用风险。公网仍需共享限流、持久化预算和真实会话/网关配置。

## 6. 技术实现

- Node.js 24、原生 HTTP/fetch、ES modules；前端为原生浏览器模块与响应式 CSS。
- `src/zhihu-knowledge.mjs`：知乎列表/详情客户端，超时、响应大小、JSON/schema、work_id 白名单和缓存处理。
- `src/content-store.mjs` / `src/server.mjs`：内容模式、静态页面、`/api/knowledge`、`/api/learn`、`/api/follow-up`、`/api/challenge`、`/api/personalize-action` 路由及生成防护。
- `src/model-client.mjs`：Responses 请求、取消/超时/上游错误分类、严格结果 schema、逐字引用校验。
- `src/demo-model-client.mjs` 与 `src/demo-server.mjs`：不联网的确定性赛前演示，不冒充正式内容或真实模型。
- `public/app.js`、`public/index.html`、`public/learning-card.js`：双入口工作台、文章级草稿隔离、异步竞态保护、挑战/场景化行动和本地 Word 导出。

## 7. 原创、归属与隐私

产品流程、页面交互、提示约束、校验逻辑和演示材料由项目自行设计实现；开发演示的两篇材料明确是项目原创、非知乎正式内容。知乎内容保留作者、标题、`work_id`、来源 URL 和“当前可读片段”边界；AI 输出不冒充作者原话。

用户复述、追问、场景和行动修改默认只在当前页面状态中保留；Word 在浏览器内生成，不上传这些文字到额外统计服务。模型凭证不进入前端、学习卡、日志或 Git；`.local/` 与 `sources/` 为本机文件，不作为交付内容。正式部署前仍需确认会话、网关、日志脱敏、共享限流和数据保留策略。

## 10. 评委可验证点

评委若获得可运行链接，可按以下顺序核验：

1. 选择列表中的一项，查看作者、标题、来源和“完整性未知/当前可读片段”提示。
2. 不填写复述直接点击“AI 帮我读懂”（若线上额度暂不可用，应显示可恢复错误，不得伪造成功）。
3. 在本地 demo 中检查核心观点、论证步骤和适用条件的引用定位，以及“原文理解/AI 延伸”标签。
4. 回答一分钟挑战，观察只反馈关键点、不打分；输入含“下周高数复习、每晚 30 分钟、卡在极限题”的场景，确认任务、完成标志、回顾安排发生具体变化。
5. 修改行动并导出 Word，检查来源、生成方式、用户文字、引用和“待尝试”状态是否保留。
6. 切换 direct/reflect 入口或文章，确认草稿隔离、旧异步结果不覆盖新内容；在生成失败时确认用户文字未被清空。

以上核验点是产品行为检查清单，不替代线上可用性、模型额度或赛事提交凭证。
